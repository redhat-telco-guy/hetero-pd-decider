Engineering detail

Let lower-cost NVIDIA cards read the long prompts, so the premium Intel Gaudi cards spend their time writing answers.

Every AI request has two jobs: reading the prompt and writing the answer. When one card does both, a single long document makes every other user on that card freeze mid-answer. Our router looks at each request as it arrives and instantly decides which card should do the reading.

Stock llm-d uses one fixed size cutoff for every request. Ours knows how fast each card is, how busy it is, and how long the network handoff takes.

How it decides, in three questions

1 · SizeIs the prompt big enough to be worth moving?Short chat messages stay where they are. Moving them costs more than it saves.
2 · LoadHow many users would wait if the answering card read it?The busier the Gaudi card, the more a long read hurts. The router reads this live, every second.
3 · Speed and deadlineIs moving it faster overall, and still on time?It adds up the NVIDIA card's read time and the network handoff, and checks the 1-second response target.
Move the reading to the NVIDIA card when it is clearly faster for everyone and meets the deadline.
Keep it on the Gaudi card when the prompt is short, the Gaudi is idle, or moving would miss the deadline.

    One request, two paths

    Every request reaches the router (llm-d EPP) first. Your plugin, hetero-pd-decider, is the step that chooses between the two paths below.

    router and your deciderprefill (A30)decode (Gaudi 3)

    Why the split matters

    Prefill reads the whole prompt at once. It's compute-heavy and bursty. Decode generates one token at a time for every running stream, and it's memory-bound and steady. When a long prompt prefills on a busy decode card, every stream on that card stalls until it finishes. Users see that as a freeze in their chat.

    Moving the prefill to another card avoids the stall, but it costs a hop: the other card's prefill time plus shipping the KV cache over the network.

    The three estimates

    U = prompt tokens not already cached on the decode pod remote = U / R_prefill + waiting_P × Q / R_prefill + U × kvBytes / bandwidth local = U / R_decode + waiting_D × Q / R_decode stall = running_D × U / R_decode (stream-seconds frozen) split when remote ≤ SLO and remote < (1 − margin) × (local + w × stall)

    R is a card's measured prefill speed in tokens per second. Q is avgQueuedPromptTokens, the work assumed behind each waiting request. With several prefill pods, the one with the lowest remote estimate is used.

    What it's worth

    A model, not a measurement. It runs each router's rule over a traffic mix, using the hardware settings from the Simulator tab, on a fixed fleet of decode and prefill cards. Every second a decode card spends prefilling is a second all its streams produce no tokens. So a router that offloads prefill well gets more output from the same fleet, as long as it stays inside the latency target. The A/B test replaces these estimates with measured numbers.

    Traffic defaults are the runbook's A/B workload: 32 chat users with 200-word prompts, plus 2,000-word prompts at 0.5 per second. The $/hour values are example rates; enter your own.
